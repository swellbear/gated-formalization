# Invent a new candidate, then cheap-test it

A short working habit. It does not change how claims are scored.

## The habit

- Invent a **new** named candidate (a class or “horse”). Do not revive one that was already burned.
- Run a **cheap test** under the frozen protocol: discovery first; confirm only if it survives discovery.
- The **Operator** (gatekeeper) admits, rejects, or parks. Lab never admits its own candidate.
- Do not fake a clear: discovery is not confirm; making the question clearer is not clearance; one board met is not another board met; do not pick the least-bad leftover; a clearer question is not a proven claim.
- Burned classes stay burned. If something survives confirm only in a narrow scope, it stays scoped — not “skill met” unless that is honestly established under the rules.
- Tiny training runs can stay light. A live invent→test should land in the trackers when the Operator decides.

## Why

New candidates are cheap to propose and easy to over-credit. A short loop — invent, cheap-test, then wait for the Operator — keeps burned ideas dead and stops a discovery pass from being treated as a prove-out.

## Where to write it

You do not need a new format. When the Operator decides a live invent→test should be recorded, a few sentences in a place you already use is enough, for example:

- the leftover list (`TRACKER_RESIDUAL_QUEUE.md` — parked unfinished items)
- the failure log (`logs/failure_mode_log.md` — what went wrong and why)
- the run’s status note (`STATUS.md` — the short “where we are” file)

This does not change the scoring rules. It is an operator habit. Sibling habit (write up what you learned before a brand-new claim): [`docs/DIGESTION_HABIT.md`](DIGESTION_HABIT.md).
