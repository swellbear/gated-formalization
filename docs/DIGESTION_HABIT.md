# Write up what you learned before jumping to a new claim

A short working habit. It does not change how claims are scored.

## The habit

- Before you start a **brand-new claim**, write down what the last one taught you. If something is still unfinished, park it clearly so it does not vanish.
- You may keep working the **same** problem for a while. When that string of tries stalls, stop and write it up. If you stay on the same problem and invent a new candidate, use the sibling habit: [`docs/INVENT_TEST_HABIT.md`](INVENT_TEST_HABIT.md).
- Tiny practice or training runs do not need the full ritual.

## Why

Useful findings die easily. They sit in draft pull requests, half-remembered chats, or a folder nobody reopens. A few plain sentences keep the useful part available for the next claim.

## Where to write it

You do not need a new format. A few sentences in any place you already use is enough, for example:

- the run’s status note (`STATUS.md` — the short “where we are” file)
- the leftover list (`TRACKER_RESIDUAL_QUEUE.md` — parked unfinished items)
- the failure log (`logs/failure_mode_log.md` — what went wrong and why)

This does not change the scoring rules. It is an operator habit.
